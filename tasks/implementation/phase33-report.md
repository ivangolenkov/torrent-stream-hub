# Phase 33: Временные Торренты И Автоматическая Очистка (Отчёт)

## 1. Что Сделано

- `internal/repository/migrations/0004_temporary_torrents.sql`: добавлены `is_temporary`, сохранённый deletion manifest с признаком готовности, таблица FIFO с `AUTOINCREMENT` и триггеры её жизненного цикла. Старые записи остаются постоянными; одинаковые timestamps не меняют порядок новых добавлений.
- `internal/models/torrent.go`: собственные REST/SSE ответы содержат явный `is_temporary`, включая `false`.
- `internal/repository/torrent_repo.go`, `cleanup.go`: выделены сохранение с политикой, закрепление, выборка FIFO и сохранение намерения/точного списка удаления. Статистический upsert не изменяет политику. Удаление транзакционно очищает также files, viewed_history и FIFO-запись.
- `internal/usecase/temporary.go`, `torrent_uc.go`: реализованы монотонное постоянство, лимит, FIFO-очистка после нового временного добавления, при старте и с периодом повтора 5 секунд. Ошибки cleanup не отменяют успешный add. Общая lifecycle-блокировка согласует add/pin/delete/restore/изменения состояния с SyncWorker и приёмом передач; не удерживается на время передачи видео или разрешения HTTP-ссылки.
- `internal/usecase/temporary_files.go`: пути вычисляются из подтверждённых metainfo через штатный `storage.DefaultFilePathMaker`, а не через угадывание по имени. Намерение удаления сохраняется до Drop; окончательный manifest — после остановки движка, до unlink. Это учитывает получение metadata в момент остановки и допускает безопасный повтор после частичного удаления/рестарта.
- Автоочистка удаляет только перечисленные payload/`.part` и пустые родительские каталоги через `os.Root`. Traversal, symlink, нештатные файловые типы, общие пути, реальные файловые aliases и пересечения с хранилищем приложения приводят к отказу от удаления.
- `internal/engine/cleanup.go`: определён список защищённых путей приложения, включая piece-completion DB, SQLite и её sidecars, metainfo, логи и retrackers.
- `internal/usecase/sync_worker.go`: снимок движка и сохранение согласованы с lifecycle; DB-missing записи не вставляются обратно. Ошибка чтения БД не публикует ложное пустое состояние или предполагаемую политику.
- `internal/delivery/http/torrserver/handlers.go`: `save_to_db` применяется во всех ветках `add`; HTTP `.torrent` сразу сохраняется с правильной политикой. Streaming и preload получают lease, в том числе асинхронный warmup.
- `internal/delivery/http/api/handlers.go`, `download_handlers.go`: добавлено идемпотентное действие `make_permanent`; одиночные/архивные HTTP-download защищены lease. Собственное добавление и multipart upload создают постоянные записи или закрепляют временные.
- `internal/config/config.go`, `cmd/hub/main.go`: настройка `HUB_MAX_TEMPORARY_TORRENTS` / `--max-temporary-torrents`, default 3, строгая проверка положительного целого и приоритет CLI. Startup-cleanup выполняется до запуска HTTP; фоновая работа завершается до закрытия engine/БД.
- `web/src/components/TemporaryTorrentControl.vue`, `TorrentTable.vue`, `BottomPanel.vue`, `web/src/stores/torrentStore.ts`, `web/src/api/client.ts`, `web/src/types/index.ts`: метка «Временный», предупреждение и закрепление в desktop/mobile и деталях. Есть состояние запроса, защита повторного клика, вывод ошибки, защита подтверждённого pin от старого SSE в полёте и очистка выбранной записи/кешей при автоудалении.
- Обновлены `README.md`, `docker-compose.yml`, статус и DoD исходной фазы. Добавлены unit/integration/HTTP тесты конфигурации, repository, usecase и обоих API.

## 2. Зафиксированное Поведение

- TorrServer `add` с `save_to_db: false` или без поля создаёт временный торрент; `true` закрепляет. Постоянный никогда не становится временным от повторного `false`.
- Повторное добавление одного infohash не меняет FIFO и само по себе не запускает очистку. После удаления новое добавление получает новую FIFO-позицию.
- Существовавшие до миграции записи, собственный Web GUI/API и multipart upload — постоянные.
- FIFO блокируется старейшим защищённым кандидатом: более новые не удаляются вместо него. Защищены reader/direct streaming, preload, HTTP-download и десятисекундное окно после передачи; существующий QoS/debounce движка не изменён.
- Настройка требует рестарта; `0`, отрицательные, нечисловые значения и переполнение недопустимы. Снижение лимита применяется при старте.
- Сбой очистки логируется, запись остаётся видимой, работа сервиса и успешный add продолжаются. При сохранении намерения удаления кандидат помечается paused. Повтор ограничен периодом 5 секунд.
- Незавершённый manifest после сбоя БД/остановки требует подтверждённых metadata перед повтором; пустота списка не угадывается. При необходимости пользователь может возобновить загрузку metadata или закрепить торрент.
- При общих/неизвестных путях действует консервативный отказ. В частности, metadata-pending другой торрент может задержать удаление файлов кандидата, пока невозможно доказать отсутствие пересечения.
- CORS `*` и контракты остальных действий TorrServer сохранены. Новая аутентификация не добавлялась.

## 3. Проверки И Результаты

Успешно выполнено на macOS arm64:

```bash
go test -count=1 ./...
go test -race -count=1 ./internal/repository ./internal/usecase ./internal/config ./internal/delivery/http/... ./internal/engine ./cmd/hub
go vet ./...
go build -o <temporary-directory>/hub ./cmd/hub
cd web
npm run build
```

`git diff --check` также проходит. Race detector не обнаружил гонок. Как и в предыдущей фазе, macOS linker при race-линковке torrent dependency предупреждает о `malformed LC_DYSYMTAB`; команды завершаются успешно.

Автоматически проверены:

- миграция заполненной старой БД без потери метаданных/файловых записей, WAL, FIFO при одинаковом времени, сохранение порядка при переоткрытии БД, новая позиция после delete/re-add;
- default/env/CLI/валидация лимита; FIFO и закрепление, отсутствие понижения постоянства, неизменность очереди и отсутствие cleanup при ошибке/повторе add;
- удаление single/multi-file payload, `.part`, сохранность посторонних файлов и постоянных записей;
- durable manifest и повтор частичного удаления после полного закрытия и пересоздания engine/SQLite, startup после снижения лимита;
- инъекция ошибки БД при финализации manifest: add успешен, данные не удаляются до durable-сохранения, после устранения ошибки retry завершается;
- отказ при traversal, symlink, директории вместо файла, общих путях, case-alias на case-insensitive FS и попытке удалить служебную completion DB;
- lease, идемпотентный release, debounce, блокировка FIFO старейшим активным торрентом и фоновый повтор без нового добавления;
- HTTP-передачи с заблокированным writer: disk-stream, reader fallback, file-download, torrent-download и preload не вытесняются новым временным торрентом;
- конкурентные add/pin/transfer/cleanup/SyncWorker, явный JSON/SSE-признак и отсутствие вставки DB-missing записи из движка;
- все варианты TorrServer link (magnet, hash, HTTP `.torrent`, HTTP magnet text/redirect), отсутствующий флаг/true/false, закрепление через native add и multipart upload;
- API pin: `200`, повторный `200`, `404` и ошибка БД `500`; существующие HTTP/CORS и streaming regression tests продолжают проходить.

### Браузерная Проверка

На изолированной временной БД запущен собранный сервер с embedded Web GUI. Проверка выполнена через Playwright, без изменения пользовательских downloads/config:

- четыре временных add дают три записи, первый удалён;
- desktop-кнопка закрепляет торрент, REST подтверждает `is_temporary: false`;
- на viewport 390×844 доступны метка и закрепление в мобильной карточке/деталях;
- моделируемый HTTP `500` показывает ошибку и не переключает признак; повторный успешный запрос закрепляет;
- при задержанном ответе кнопка disabled, повторный программный click не создаёт второй запрос;
- автоудаление выбранного временного закрывает панель деталей через SSE; постоянные сохраняются, временных остаётся 3.

Тестовый сервер остановлен. При остановке с открытым SSE соединением сработал существующий десятисекундный HTTP shutdown timeout с последующим принудительным закрытием; cleanup worker и engine завершились. Это существующий lifecycle HTTP/SSE, не изменение этой фазы.

## 5. Уточнения И Ограничения

- Существенных функциональных отклонений от плана нет. Вместо перестройки основной таблицы torrents FIFO реализован отдельной таблицей с `AUTOINCREMENT`; политика изменяется явно, отдельно от статистического upsert.
- Сохраняемый двухэтапный manifest добавлен для выполнения требований к частичному удалению, ошибкам БД и metadata race при Drop. Неподтверждённая принадлежность данных блокирует очистку, а не ослабляет безопасность ради лимита.
- Рекурсивная существующая ручная очистка по имени не переиспользуется автоматической очисткой. Новая логика не удаляет произвольные orphan-файлы, metainfo-кеши и служебные БД; цель фазы — payload временных торрентов и связанные записи.
- Синхронизация lifecycle кратковременно сериализует мутации и дисковую очистку. Передачи не удерживают её, но массовое удаление большого числа файлов может задержать новую мутацию/приём новой передачи до завершения прохода.
- Новая инфраструктура frontend unit tests не вводилась: сборка/typecheck автоматические, пользовательские сценарии проверены в браузере через Playwright. Ручная приёмка на реальном Smart TV/Lampa/NAS и отдельный прогон Windows/Linux не выполнялись.
