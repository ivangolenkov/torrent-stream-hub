# Сравнение хранения и восстановления с qBittorrent

Дата: 2026-10-25. Статус: исследование завершено; изменения runtime, БД и загрузок не выполнялись. Фаза 42 не начата.

На основании исследования подготовлен [план фазы 42](../phase42-readable-storage-and-file-recovery.md). Планирование не означает начала реализации.

Проверены исходники Torrent-Stream-Hub на `2c0cbe390b1df7e7e0730234fed030ddc9cc3f58` и qBittorrent на [`a87f8f9c282e7341b1f4f9e9a5a66c869d2366a6`](https://github.com/qbittorrent/qBittorrent/commit/a87f8f9c282e7341b1f4f9e9a5a66c869d2366a6), полученном как HEAD master, с датой коммита 2026-10-20. Это сравнение реализации, а не измерение производительности запущенных клиентов. qBittorrent использует libtorrent-rasterbar; наш клиент — локальный fork anacrolix/torrent. Поведение libtorrent зависит от версии сборки; детали fast resume ниже не подразумевают одинаковую проверку файловых атрибутов во всех версиях.

## Основной вывод

Переход к понятным именам каталогов обоснован. Привязка к SQLite уже реализована: `torrent_storage(hash, version, root, state, manifest, error)`. Проблема — жёсткое ограничение значения `root`: только `payload/<40 hex>`. Следует развить существующий storage mapping, сохранив изоляцию разных торрентов, проверку владения и восстановление незавершённых операций.

Наиболее полезные изменения: человекочитаемые пути, более выразительная проекция состояния файлов, отдельный прогресс выбранных файлов и явные операции перемещения/поиска данных. Fast resume — самостоятельное изменение политики доверия к диску, а не необходимое условие нового layout.

## Пути: что именно следует изменить

`payload.Root()` формирует хешевый каталог, а `payload.ValidRoot()` отвергает остальные имена. Production resolver действительно читает SQLite, но затем применяет эту проверку. Дополнительно `VerifyStorageProgress()`, резервирование новых торрентов, migration targets и fallback coordination keys сами вычисляют корень из hash. Замена только `Root()` или одной строки БД недостаточна.

Предлагаемый результат:

```text
downloads/
  payload/
    Interstellar (2014)/
      Interstellar.2014.1080p.mkv
    Example Series - Season 01/
      S01E01.mkv
      S01E02.mkv
    Example Series - Season 01 (2)/
      S01E01.mkv
```

`payload/` можно сохранить как уже выделенное пространство пользовательских данных. Каталог торрента получает понятное имя, а hash остаётся идентификатором в БД и именем служебного metainfo. Разным торрентам нельзя автоматически разрешать совместную запись в один файл только из-за совпадения названия.

Необходимо явно разделить:

- **Идентичность:** стабильная запись торрента и её v1/v2 aliases. Наш `record_id` уже защищает от старых операций после delete/re-add.
- **Представление:** `name`/`title`, которые пользователь может менять без перемещения данных.
- **Расположение:** сохранённый относительный `root`, layout и его revision. Этот путь выбирается один раз и изменяется только операцией перемещения.
- **Каталог metainfo:** исходные пути, размеры, индексы, offsets и hashes остаются неизменными.
- **Физический путь файла:** результат явной раскладки; при поддержке индивидуальных переименований — отдельный mapping по индексу файла.

Для первого шага достаточно версии layout и сохранённого правила обработки общего корня metainfo. Полная таблица переименований каждого файла нужна только при введении такой функции. Например, `Series/episode.mkv` внутри metainfo не должен случайно стать `payload/Series/Series/episode.mkv`: снятие общего префикса должно быть частью layout, а не эвристикой при каждом открытии. Однофайловые, многофайловые, v1, v2 и hybrid структуры требуют отдельных примеров.

Коллизии разрешаются при резервировании: суффикс `(2)` либо короткий hash только при необходимости. Выбранное имя сохраняется. Учитываются регистр на целевой ФС, Unicode, запрещённые Windows-имена, длина компонента и уже существующие чужие каталоги. Одного SQL `UNIQUE(root)` в нынешней таблице недостаточно: hybrid aliases намеренно разделяют один root. Уникальность должна относиться к владельцу storage location, с проверкой пересечения путей.

Для magnet без metadata желательно сначала разрешить получение metadata, затем выбрать и зарезервировать путь до первого payload write. Текущее резервирование происходит раньше получения metadata: это отдельная граница для переработки. `dn` можно использовать как очищенную подсказку, но не как источник файловой идентичности или разрешение на использование занятого каталога.

## Состояния и отображение прогресса

Наше разделение intent/runtime/activity стоит сохранить. `Paused` может сочетаться с чтением уже проверенного локального файла; стриминг не отменяет фоновые операции, а сохранённая команда enabled означает участие в планировщике. Копировать весь enum qBittorrent в бизнес-логику не требуется.

Нужна более понятная пользовательская проекция: «Получение метаданных», «Ожидание слота», «Нет передачи», «Проверка», «Перемещение», «Выбранные файлы готовы». Причина отсутствия передачи должна опираться на наблюдения; нулевая мгновенная скорость не доказывает отсутствие пиров. Проверка/стриминг/блокировка остаются независимыми полями, даже если GUI выбирает одну основную подпись.

Сейчас `mapManagedTorrent()` вычисляет `downloaded` из проверенных pieces и выставляет ноль при checking/uncertain. Detached projection сохраняет last-known наблюдения с их provenance. В GUI уже есть подписи источника прогресса, но у строки файла нет самостоятельного состояния проверки и причины недоступности. Источники: [health.go](../../internal/engine/health.go), [read model](../../internal/usecase/read_model.go), [progress.ts](../../web/src/progress.ts), [BottomPanel.vue](../../web/src/components/BottomPanel.vue).

Предлагаемые независимые поля файла:

| Поле | Назначение |
| --- | --- |
| `priority` / selection | Устойчивая настройка пользователя; stream overlay её не переписывает |
| `verified_bytes` | Подтверждённые данные текущего открытия |
| `last_known_bytes`, время наблюдения | Исторический прогресс для объяснения состояния после рестарта |
| `verification` | Unknown / queued / checking / verified / failed, с отдельным прогрессом прохода |
| `presence` | Unknown / present / missing; отсутствие нового незагруженного файла не равно потере данных |
| `direct_read_ready` и причина | Доступность полного файла для direct path; операция чтения всё равно повторно проверяет условие |
| `activity` | Фактическая загрузка/чтение и временный streaming priority |

Эти поля — предлагаемая read model, не новые persistable команды. `Skip` совместим с уже готовым файлом; наличие файла и размер не доказывают корректность; playable media flag не доказывает готовность к HTTP-чтению. Для v1 piece может пересекать границу файлов, поэтому готовность нельзя определять только по локальному размеру или собственной записи файла.

Показательный существующий сценарий: один из двух равных файлов выбран и загружен. Сейчас получаются `selection_complete=true`, `progress=50`, `state=Queued`; это зафиксировано `TestPartialSelectedCompletionDoesNotBecomeSeeding`. Предлагается показывать «Выбрано: 100%; весь торрент: 50%». Не объявлять торрент полным seed и не отнимать слот у следующей загрузки. Источник: [phase38_runtime_test.go](../../internal/engine/phase38_runtime_test.go).

## Рестарт, проверка и восстановление

У нас startup читает записи по FIFO, проверяет storage/recovery, восстанавливает intent и приоритеты, затем подключает runtime. Paused и записи с activation blocks восстанавливаются offline из сохранённого metainfo. Активное восстановление умеет использовать metainfo, затем source URI и hash fallback. HTTP уже слушает во время startup, но torrent API защищён readiness gate до окончания начальной процедуры; это не означает ожидание завершения всех фоновых hash-проходов. Источники: [startup](../../cmd/hub/main.go), [restore](../../internal/usecase/torrent_uc.go), [inactive restore](../../internal/usecase/inactive_restore.go).

`VerifyOnOpen` использует свежие признаки текущего открытия вместо сохранённой `piece_completion`. Внутри процесса проверяются identity/size/mtime файлов, изменения отзывают зависимые pieces. Ограничение уже есть: два активных hashers глобально и один на торрент. Повторная проверка не должна самовольно снимать пользовательскую паузу, DiskFull или другой независимый запрет. Источники: [file-torrent.go](../../pkg/anacrolix-torrent/storage/file-torrent.go), [file-piece.go](../../pkg/anacrolix-torrent/storage/file-piece.go), [recheck](../../internal/engine/recheck.go), [SQLite hints](../../internal/completion/sqlite.go).

Fast resume libtorrent сохраняет карту pieces и незавершённые блоки. Это уменьшает работу после рестарта, но не эквивалентно новому доказательству целостности каждого байта. [Контракт fast resume][L1]. В qBittorrent обработчик rejected resume отмечает MissingFiles, а force recheck сбрасывает прежний прогресс для нового прохода. [Обработка восстановления][Q3]. Не следует обещать, что любой аварийный выход qBittorrent обязательно вызывает полную проверку или, наоборот, всегда обходится без неё.

Для NAS предлагается отдельное исследование ускорения старта:

1. Сначала измерить время до API readiness, до первого проверенного воспроизводимого диапазона и до завершения общего прохода; учитывать HDD/SSD, количество файлов и объём повторного чтения.
2. Улучшить очередь проверки по физическому устройству и приоритет нужных плееру файлов/диапазонов. Сохранять проверку перед чтением и учитывать соседние файлы общего piece.
3. Только отдельным решением вводить fast resume с явной политикой доверия: checkpoint generation, identity storage, bitmap, file signatures и корректный порядок flush/commit.
4. Checkpoint нельзя объявлять надёжным только по флагу clean shutdown. Повторные записи после checkpoint, смена mapping, импорт, move и аварийный выход требуют отзыва доверия до новых записей. Same-size/mtime изменение внешней программой может быть неразличимо; режим с новым hash-проходом должен сохраняться.

Есть отдельная диагностическая разница. Наш `detectMissingExpectedPayload()` обнаруживает физическое исчезновение файла, ранее подтверждённого в текущем runtime; это не полный startup inventory ранее завершённой библиотеки. Из кода следует, что исчезновение до нового открытия нельзя всегда отличить от обычной недокачанности по одному этому механизму. Источник: [missing_payload.go](../../internal/engine/missing_payload.go). Стоит хранить ожидаемое наличие файлов отдельно от доверия к их содержимому и проверять доступность ожидаемого тома. На NAS отсутствующий mount нельзя автоматически принимать за новую пустую папку для повторного скачивания.

Полезная пользовательская операция — «Указать, где находятся существующие данные» с read-only проверкой кандидата, затем изменением mapping. Она должна быть отделена от «Переместить данные» и «Докачать отсутствующие части».

## Миграция понятных каталогов

Это развитие текущего журнала, а не безусловный rename при запуске:

1. Поддержать одновременно старый hash layout и новый layout. Старые записи продолжают открываться без массового обязательного переноса.
2. Сформировать план source → target, проверить конфликт имён/владения, aliases и незавершённые recovery операции. Зарезервировать обе стороны и записать durable intent с record ID, mapping revision и ожидаемой identity файлов.
3. Остановить новые операции записи/чтения для перемещаемого storage, завершить активные readers либо отложить перенос. Закрыть runtime/storage и дождаться фоновых задач. Пользовательский run intent сохранить отдельно.
4. На одной ФС применить rooted no-replace rename, если переносится именно каталог с прежней внутренней раскладкой. Для изменения внутренней структуры нужен отдельный manifest. Реализовать нативные гарантии и flush каталогов для поддерживаемых ОС.
5. Между ФС — copy, проверка целостности копии и durability, публикация без перезаписи. Неполные pieces остаются неполными. Переключить mapping только после подтверждения результата.
6. Завершить mapping commit и cleanup по журналу. После падения между FS mutation и SQL commit исследовать обе стороны по сохранённой identity; при неоднозначности остановить операцию с сохранением данных. Не выбирать копию по имени или размеру.
7. Подключить runtime с новым mapping и прежними приоритетами/intent. Перенос сам по себе не даёт readiness. Для первой реализации сохранить текущую проверку при открытии.

Текущий legacy migration всегда копирует, проверяет и только после mapping commit чистит исходник. Он не содержит готовой оптимизации directory rename. Для внедрения новой раскладки нужно переработать также verifier, cleanup manifests, direct HTTP path, ownership/coordinator keys и legacy recovery. Простое увеличение `LayoutVersion` сломает места с проверкой равенства единственной версии — нужны version-aware resolver и валидаторы.

## Другие идеи и последовательность работ

| Приоритет | Предложение | Основание |
| --- | --- | --- |
| 1 | Versioned mapping с понятными именами, layout и безопасным move | Непосредственно решает проблему пользователя; уже есть основа в SQLite |
| 2 | File availability/readiness reasons, selected progress, отдельный verification progress | Устраняет двусмысленность «0%», «Queued» и «файл существует» |
| 3 | Locate existing data, startup inventory и проверка ожидаемого тома | Помогает восстанавливать NAS после смены mount/path |
| 4 | Метрики и очередь disk/hash jobs с приоритетом стриминга | Уменьшает конкуренцию за HDD; глобальные лимиты hashers уже есть |
| 5 | Опциональный fast resume с отдельным контрактом и тестами сбоев | Может сократить чтение после старта; меняет модель доверия |
| Позже | Категории как политика размещения; отдельные incomplete/completed locations; индивидуальное rename | qBittorrent даёт полезный пример: [контракт путей][Q1], [категории][Q2]; для HTTP-стриминга дополнительные перемещения требуют координации readers |

У qBittorrent стоит взять разделение путей и раскладки, явные операции перемещения и детальную проекцию состояния. Наши durable intent, независимые safety blocks, generation fencing, journals, отсутствие автоматического `.part` и range-aware QoS следует сохранить. Прямой перенос libtorrent API в anacrolix невозможен без адаптации; замена движка для решения проблемы имён не требуется.

Новая реализация не выполнялась, поэтому runtime-тесты и benchmark не запускались. Прочитаны существующие регрессии restore/selection/verification/migration; это не заявление об их повторном успешном выполнении. Отчёт фазы 41 остаётся отдельным источником её приёмки.

Для будущего DoD: duplicate names и case collisions; одно-/многофайловые v1/v2/hybrid; magnet без имени; coexistence старого/нового layout; paused, DiskFull и partial selection после рестарта; crash перед/после rename и SQL commit; целевой конфликт; EXDEV и заполненный диск; активный Range stream; delete/re-add со старым worker; partial/zero-length/shared-boundary files; потерянный mount; unchanged-size corruption. Нужны существующие root/fork suites и нативные storage проверки поддерживаемых ОС.

Рекомендации в этом отчёте — вывод для архитектуры Torrent-Stream-Hub, а не утверждение, что qBittorrent реализует предложенный здесь протокол миграции или гарантии нашего HTTP-стриминга.
