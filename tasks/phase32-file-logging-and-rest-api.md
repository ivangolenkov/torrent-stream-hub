# Phase 32: Файловое Логирование, Суточная Ротация И REST API Логов

## Статус И Предпосылки

- Статус: запланировано; этот документ не является отчётом о реализации.
- Реализацию начинать после проверки DoD Phase 31 и отчёта `tasks/implementation/phase31-report.md`.
- Пользовательский сценарий: при периодических ошибках необходимо получить сохранённые логи за нужную дату или последние N строк без доступа к консоли сервера.

## Описание

Сохранить вывод в консоль и дополнительно записывать логи в файлы с текущей датой в имени. Каждый календарный день используется отдельный файл. Старые файлы автоматически удаляются согласно настраиваемому сроку хранения, по умолчанию — три предыдущих дня плюс текущий.

Добавить REST endpoint для чтения логов с фильтрацией по дате/диапазону дат и выборкой последних N строк (разовый `tail`, не `tail -f`). Реализация должна экономно использовать память и не требовать SQLite, mmap или изменений торрент-движка.

## Основания В Текущем Коде

- `internal/logging/logging.go`: собственный логгер с уровнями, текстовым форматом, выводом в stdout и маскированием чувствительных query-параметров.
- `cmd/hub/main.go`: инициализация логирования и сообщения через стандартный `log`, в том числе ошибки запуска.
- `internal/delivery/http/router.go`: используются `chi` middleware.Logger и собственный обработчик panic; CORS разрешает origins `*`.
- `internal/config/config.go`: есть `HUB_LOG_LEVEL`, но нет настроек файлового вывода и хранения.
- `docker-compose.yml`: `/config` уже подключён как постоянный volume и подходит для хранения логов.

## Границы Фазы

Входит:

- одновременная запись в консоль и файл;
- суточная ротация без перезапуска и дополнение файла после рестарта;
- автоматическая очистка старых файлов;
- объединение основных источников логов приложения;
- REST API чтения и эффективный tail;
- тесты, документация и отчёт.

Не входит:

- экран просмотра логов в Web GUI;
- непрерывная подписка, SSE, WebSocket и `tail -f`;
- поиск по тексту, фильтрация по уровню, сжатие архивов и ротация по размеру;
- перенаправление файловых дескрипторов stdout/stderr и гарантированный перехват аварийного вывода Go runtime;
- замена всей системы логирования на сторонний framework;
- новая система аутентификации, изменения SQLite, streaming QoS и BitTorrent protocol.

## Контракт Хранения И Настроек

### Файлы

- Имя: `hub-YYYY-MM-DD.log`, например `hub-2026-10-20.log`.
- Каталог по умолчанию: `logs` рядом с файлом БД; для `/config/hub.db` — `/config/logs`.
- Часовой пояс: локальный часовой пояс процесса; имя файла и временные метки используют одну временную зону.
- Существующий файл открывается в append-режиме; рестарт не обнуляет историю.
- Первая запись нового дня попадает в новый файл. Отдельно создавать пустой файл ровно в полночь не требуется.
- Сохраняются текущий текстовый формат, уровни и маскирование чувствительных параметров. Многострочные сообщения и stack trace допустимы.
- Рекомендуемые права нового каталога — `0700`, новых файлов — `0600`; существующие права автоматически не менять.

### Конфигурация

Добавить env/CLI настройки:

| Env | CLI | Значение по умолчанию |
| --- | --- | --- |
| `HUB_LOG_DIR` | `--log-dir` | `logs` рядом с БД |
| `HUB_LOG_RETENTION_DAYS` | `--log-retention-days` | `3` |

- CLI имеет приоритет над env, как в остальных настройках проекта.
- Срок хранения задаёт количество предыдущих календарных дней; `0` сохраняет только текущий день, отрицательные значения недопустимы.
- Пример: 20 октября при значении `3` сохраняются файлы за 17–20 октября, файлы за 16 октября и ранее удаляются.
- Возраст определяется датой в имени, не `mtime` и не интервалом в 72 часа. Учитывать календарные дни, включая переходы часового пояса/DST.
- Очистка выполняется при запуске и периодически (например, раз в час), даже при отсутствии новых логов.
- Удалять только обычные файлы с точным шаблоном имени и корректной датой; не трогать посторонние файлы, каталоги, symlink и активный файл записи.

## Контракт REST API

### `GET /api/v1/logs`

Успешный ответ: `200`, `Content-Type: text/plain; charset=utf-8`, `Cache-Control: no-store`.

| Параметр | Значение |
| --- | --- |
| `date=YYYY-MM-DD` | Один календарный день |
| `from=YYYY-MM-DD&to=YYYY-MM-DD` | Диапазон дат включительно |
| `tail=N` | Последние N строк выбранных файлов |

Правила:

- Без параметров даты выбирается текущий день.
- `date` несовместим с `from`/`to`; для диапазона обязательны оба параметра и `from <= to`.
- Формат дат строгий, с проверкой реального календарного значения.
- Повторяющиеся известные параметры, пустые значения и некорректные комбинации отклоняются с `400`.
- `tail` — положительное целое число; предлагаемый максимальный размер — 100 000 строк, большее значение даёт `400`.
- Файлы объединяются в порядке дат; строки внутри файла сохраняют исходный порядок.
- `tail` применяется ко всей выборке, а не отдельно к каждому файлу; результат возвращается от старых строк к новым.
- Если строк меньше N, вернуть все доступные. Stack trace считается несколькими физическими строками.
- Последняя строка без завершающего перевода строки учитывается; завершающий `\n` не создаёт дополнительную пустую строку.
- Если подходящих файлов нет — `404`; существующий пустой файл даёт `200` с пустым телом.
- Отсутствующие даты внутри диапазона пропускаются, если есть хотя бы один подходящий файл.
- Ошибки до начала ответа возвращаются через существующий JSON-контракт ошибок; после начала тела JSON не дописывается.
- Не возвращать содержимое произвольных путей, листинг каталога или внутренние пути в ошибках.
- Сохранить CORS `*` и применяемую к management API политику доступа. Если аутентификация фактически не подключена, явно описать доступность логов всем клиентам с сетевым доступом; не считать наличие `HUB_AUTH_ENABLED` гарантией защиты без проверки реализации.

Примеры:

```http
GET /api/v1/logs
GET /api/v1/logs?date=2026-10-19
GET /api/v1/logs?tail=200
GET /api/v1/logs?date=2026-10-19&tail=200
GET /api/v1/logs?from=2026-10-18&to=2026-10-20&tail=500
```

## План Работ

### 1. Настройки И Lifecycle

**Изменить:** `internal/config/config.go`, тесты конфигурации, `cmd/hub/main.go`.

- Добавить настройки каталога и хранения, defaults и валидацию без потери допустимого значения `0`.
- Инициализировать файловое логирование до запуска БД и engine, чтобы сохранить ошибки дальнейшего старта.
- Предусмотреть явное закрытие writer и остановку фоновой очистки после завершения HTTP/engine; не оставлять goroutine и дескрипторы.
- Учесть, что `log.Fatal` вызывает `os.Exit` и не выполняет defer: обеспечить сохранение startup errors и описать/скорректировать порядок выхода без масштабного рефакторинга main.

### 2. Writer, Ротация И Очистка

**Изменить:** `internal/logging/logging.go`.

**Добавить:** файлы writer/retention в `internal/logging/` и их тесты.

- Реализовать потокобезопасную запись целых сообщений, ротацию и append без взаимного перемешивания конкурентных записей.
- Дублировать сообщения независимо: ошибка файловой записи не должна отменять вывод в консоль.
- При недоступном каталоге, ошибке открытия/записи и заполнении диска продолжать работу с консольными логами.
- Сообщать об отказах файлового вывода/очистки напрямую в stderr, без рекурсии и бесконтрольного повторения одного сообщения.
- Предусмотреть ограниченные по частоте повторные попытки восстановления файлового вывода после временной ошибки.
- Не выполнять fsync на каждую строку и не накапливать неограниченный буфер. Чтение логов должно видеть уже завершённые записи без ожидания shutdown.
- Вынести получение времени для тестирования смены даты и retention без реального ожидания.

### 3. Объединение Источников

**Изменить:** `cmd/hub/main.go`, `internal/delivery/http/router.go`, при необходимости добавить HTTP logging middleware.

- Подключить стандартный `log` и HTTP access logs к общей записи, исключая дублирование префиксов и ANSI escape-последовательности в файлах.
- Сохранить логирование request ID, метода, безопасного URL/пути, статуса, объёма и длительности; не записывать Authorization, пароли и неочищенные query-секреты.
- Сохранить stack trace обработанных HTTP panic.
- Проверить фактическую конфигурацию логгера anacrolix и подключить его штатный вывод, если он обходит общий writer, без изменения локального fork и без включения дополнительных шумных уровней.
- Маскирование применять до записи в оба назначения; обход через стандартный `log` не должен раскрывать скрываемые параметры.
- Access log запроса чтения логов записывать после завершения ответа, чтобы не включать сам запрос в выдачу бесконечным циклом.

### 4. Чтение, Tail И HTTP Handler

**Добавить:** модуль чтения логов в `internal/logging/`, handler и тесты в `internal/delivery/http/api/`.

**Изменить:** регистрацию API routes и передачу зависимости чтения из startup-кода.

- Передавать reader через небольшой интерфейс/зависимость; HTTP-слой не должен самостоятельно угадывать путь логов.
- Выбирать только безопасно открытые обычные файлы внутри настроенного каталога; исключить traversal и symlink escape.
- Получить список файлов и зафиксировать верхнюю границу чтения по размеру открытых файлов до отправки тела; не следовать за новыми дописываемыми данными.
- Копировать полную выборку потоково. Для tail читать блоки с конца последних файлов, определить начальное смещение и затем потоково отдать выбранный диапазон; не собирать все строки в памяти.
- Не использовать ограничение `bufio.Scanner` на длину строки и не обрезать длинные сообщения молча.
- Согласовать открытие файлов с retention, не удерживая mutex writer во время сетевой передачи. Очистка и ротация не должны ломать уже начатое чтение или блокировать запись на время медленного HTTP-клиента.
- Уважать отмену контекста запроса и освобождать все дескрипторы во всех ветках.
- Снимок по размеру не является транзакционным snapshot всех файлов; документировать семантику последней незавершённой строки и использовать её одинаково в full/tail.

## Тестирование

- Writer: вывод в оба назначения, append после рестарта, смена суток, конкурентные записи, многострочные сообщения и маскирование для каждого подключённого источника.
- Retention: точная граница трёх дней, `0`, календарные переходы/DST, очистка при запуске и без новых записей, сохранность посторонних файлов/symlink/активного файла.
- Ошибки: недоступный каталог, моделируемая ошибка записи/ENOSPC, ошибка удаления, продолжение консольного вывода и восстановление без рекурсивного спама.
- Reader: один день, диапазон, пропуски дат, пустой файл, tail нескольких файлов, N больше доступных строк, пустые строки, очень длинная строка и отсутствие финального `\n`.
- HTTP: формат и порядок ответа, строгая валидация, `400/404/500`, CORS, `no-store`, защита путей, отмена запроса и согласованность снимка при конкурентной записи/ротации/очистке.
- Lifecycle: повторное безопасное закрытие, отсутствие утечек goroutine/дескрипторов, отсутствие блокировки writer медленным читателем.
- Проверить на большом тестовом файле, что tail читает с конца, а потребление памяти не растёт пропорционально размеру всех логов или длине выбранной строки.
- Выполнить `go test ./...`, race-тесты затронутых пакетов, `go vet ./...` и `go build ./cmd/hub`.
