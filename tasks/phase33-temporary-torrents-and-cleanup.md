# Phase 33: Временные Торренты И Автоматическая Очистка

## Статус И Предпосылки

- Статус: реализовано и проверено; отчёт — `tasks/implementation/phase33-report.md`.
- Реализацию начинать по отдельной команде пользователя после проверки DoD Phase 32 и отчёта `tasks/implementation/phase32-report.md`.
- Пользовательский сценарий: торренты из Lampa и других TorrServer-клиентов не должны бесконечно накапливаться на диске. Пользователь может сохранить нужный торрент, исключив его из автоматической очистки.

## Описание

Учитывать `save_to_db` при добавлении через TorrServer-совместимый `POST /torrents`: значение `false` означает временный торрент, `true` — постоянный. Временные торренты также сохраняются в SQLite и восстанавливаются после рестарта, но при превышении лимита автоматически удаляются вместе со скачанными файлами в порядке FIFO.

Добавить настройку максимального количества временных торрентов, по умолчанию — 3, и действие Web GUI «Сделать постоянным». Повторное добавление того же торрента с `save_to_db: true` также закрепляет его.

## Основания В Текущем Коде

- `internal/delivery/http/torrserver/handlers.go`: `TorrentsReq.SaveToDB` принимается, но не используется; `addTorrent()` поддерживает magnet, infohash и HTTP(S)-ссылки на magnet/метаданные.
- `internal/usecase/torrent_uc.go`: добавление всегда сохраняет запись в БД; `Delete(hash, true)` удаляет торрент, файлы и запись. Есть проверки относительных путей, но автоматическое удаление требует отдельной проверки фактического storage layout, общих путей и symlink.
- `internal/repository/torrent_repo.go`: upsert обновляет статистику и метаданные; `created_at` используется для сортировки, но не представлен в модели.
- `internal/usecase/sync_worker.go`: периодически сохраняет снимок движка и передаёт список через SSE. Устаревший снимок не должен воскрешать удалённые записи или менять политику хранения.
- `internal/delivery/http/api/handlers.go`: собственный API уже имеет маршрут действий `POST /api/v1/torrent/{hash}/action`.
- `web/src/components/TorrentTable.vue`, `BottomPanel.vue`, `web/src/stores/torrentStore.ts`: существующие элементы списка, деталей и обновления состояния.

## Границы Фазы

Входит:

- постоянный признак временности, миграция существующей БД и FIFO-порядок;
- обработка `save_to_db` при TorrServer `action: "add"`;
- лимит через env/CLI, очистка при добавлении и старте, повтор отложенной очистки;
- защита активной передачи файлов и согласование с жизненным циклом движка;
- закрепление через собственный API и Web GUI;
- безопасное удаление файлов, диагностика, тесты, документация и отчёт.

Не входит:

- очистка по TTL, последнему просмотру, размеру или свободному месту;
- действие «Сделать временным», корзина и восстановление удалённых данных;
- UI редактирования лимита, изменение настройки без перезапуска;
- изменение семантики TorrServer `drop`, `rem`, `wipe`, `set`;
- поиск произвольного файлового мусора вне зарегистрированных торрентов;
- изменение BitTorrent-протокола, mmap, существующей политики DiskFull или новая система аутентификации.

## Контракт Хранения

### Признак И Повторные Запросы

| Сценарий | Результат |
| --- | --- |
| Новый TorrServer `add`, `save_to_db: false` либо поле отсутствует | Временный торрент |
| Новый TorrServer `add`, `save_to_db: true` | Постоянный торрент |
| Повторный `add` временного с `true` | Становится постоянным |
| Повторный `add` постоянного с `false` либо без поля | Остаётся постоянным |
| Повторный `add` временного с `false` | Остаётся временным, FIFO-позиция не меняется |
| Добавление через собственный API/Web GUI | Постоянный торрент |
| Загрузка через `POST /torrent/upload` | Постоянный торрент; новые multipart-параметры хранения в этой фазе не вводятся |
| Записи, существующие до миграции | Постоянные |

- Идентичность определяется infohash, а не строкой ссылки: разные формы ссылки на один торрент не создают новую FIFO-позицию.
- Постоянство монотонно: никакой повторный запрос добавления не понижает постоянный торрент до временного.
- Источник истины для политики хранения — БД, а не значения по умолчанию в runtime-снимке движка.
- FIFO определяется первым успешным добавлением записи. Обновление статистики, метаданных, повторный `add`, restore и pause/resume не меняют порядок.
- Для одинакового времени добавления нужен стабильный порядок первого добавления, например сохраняемый монотонный идентификатор; одной сортировки по timestamp с точностью до секунды недостаточно.
- После удаления и нового добавления того же хеша создаётся новая позиция в очереди.
- В собственной JSON-модели и SSE передавать `is_temporary` явно, включая `false`.

### Настройка

| Env | CLI | Default |
| --- | --- | --- |
| `HUB_MAX_TEMPORARY_TORRENTS` | `--max-temporary-torrents` | `3` |

- Положительное целое число; `0`, отрицательные, нечисловые значения и переполнение отклоняются при запуске.
- CLI имеет приоритет над env. Некорректная настройка не подменяется молча значением по умолчанию.
- Изменение требует перезапуска. Уменьшенный лимит применяется при старте к существующей очереди.
- Постоянные торренты не входят в счётчик.

### Очистка И Ошибки

1. Запускать очистку после успешного сохранения нового временного торрента и при старте до приёма внешних запросов.
2. Пока число временных превышает лимит, выбирать самый старый временный торрент.
3. Атомарно относительно закрепления и начала передачи проверить, что кандидат всё ещё временный и не используется.
4. Исключить новые операции передачи/повторного добавления удаляемого экземпляра, остановить его в движке, удалить принадлежащие ему данные и затем запись БД.
5. Повторять до достижения лимита либо причины отложить очистку.

- Неуспешное добавление нового торрента не запускает удаление старых.
- Если самый старый торрент используется для просмотра/передачи, отложить очистку: не прерывать передачу и не удалять более новые вместо него. Временное превышение лимита допустимо.
- Учитывать streaming reader, direct-file fast path, preload и собственные HTTP-download endpoints. Пауза скачивания или обычная фоновая загрузка сами по себе не защищают от очистки.
- Защита распространяется на существующее debounce-окно после закрытия stream при seek. Не менять правила QoS/reference counting ради очистки.
- После освобождения защиты повторить очистку без необходимости нового `add`; допустим ограниченный по частоте фоновый повтор с корректным shutdown.
- При ошибке удаления остановить текущий проход, сохранить запись для диагностики/повтора и сообщить об ошибке в логах. Не переходить к более новым кандидатам и не выполнять бесконечный немедленный retry.
- Ошибка очистки не отменяет успешно добавленный торрент: ответ добавления остаётся успешным, превышение лимита сохраняется до повтора. Ошибки самого добавления/закрепления возвращаются клиенту как ошибки операции.
- Ошибка фоновой/startup-очистки не останавливает весь сервис; небезопасное удаление запрещено даже ради соблюдения лимита.
- Рестарт после частичного удаления должен допускать безопасный повтор. Отсутствующие файлы не являются ошибкой; постоянные записи никогда не выбираются для удаления.
- Логировать хеш, причину запуска, результат/отсрочку и ошибку без раскрытия секретов ссылок.

## Контракт API И UI

### Закрепление

```http
POST /api/v1/torrent/{hash}/action
Content-Type: application/json

{"action":"make_permanent"}
```

- Использовать общий usecase закрепления для UI и повторного TorrServer `add` с `true`.
- Ответ — `200` в существующем формате status API; повторное закрепление постоянного торрента также успешно.
- Отсутствующий торрент — `404`; ошибка сохранения — `500`; неизвестное действие сохраняет существующий контракт `400`.
- Успех означает сохранение постоянства в БД. Очистка не может удалить торрент после успешно завершённого закрепления.
- Сохранить CORS `*` и существующую политику доступа.
- Успешный TorrServer `add` сохраняет текущий формат объекта и статус `200`; менять остальные поля совместимости не требуется.

### Web GUI

- Показывать метку «Временный» в списке и подходящем представлении деталей, включая мобильный layout.
- Для временных показывать действие «Сделать постоянным» и пояснение: временный торрент может быть автоматически удалён вместе с файлами.
- На время запроса блокировать повторный клик, показывать ошибку без ложного переключения состояния.
- После успеха обновлять признак и скрывать действие; SSE не должен возвращать устаревший признак.
- При автоматическом удалении убирать торрент из списка и корректно очищать выбранный торрент/панель деталей.

## Тестирование

- Repository: миграция заполненной старой БД, временность, FIFO при одинаковом времени, повторные upsert, закрепление, рестарт и сохранение порядка.
- Очистка: четвёртый временный удаляет первый и его файлы; настраиваемый лимит; постоянные не учитываются; превышение на несколько записей после снижения лимита устраняется при старте.
- Повторное добавление: все комбинации постоянства, неизменность FIFO, разные ссылки на один хеш, отсутствие очистки после ошибки добавления.
- TorrServer: отсутствующий флаг, `false`, `true`, все поддержанные источники link; регрессионный тест, ранее проверявший сохранение при `false`, обновить под новую семантику хранения.
- Собственный API/upload: постоянство новых торрентов и закрепление существующих временных; `make_permanent`, идемпотентность, `404/500`, JSON/SSE и CORS.
- Активные передачи: reader/direct stream, preload, HTTP download, debounce после seek; FIFO блокируется старейшим активным кандидатом, очистка продолжается после освобождения без нового добавления.
- Конкурентность: add/закрепление/очистка/ручное удаление/SyncWorker и начало stream, отсутствие воскрешения записи, гонок, deadlock и сброса признака.
- Ошибки: отказ БД, файловой операции и частичное удаление, retry после рестарта, успех add при отдельном сбое cleanup, отсутствие бесконтрольных повторов.
- Файловая безопасность: single/multi-file storage, `.part`, неполученные metadata, traversal, symlink, одноимённые/общие пути и сохранность посторонних/постоянных файлов.
- Frontend: метка, закрепление, повторный клик, ошибка, SSE, исчезновение выбранного торрента, desktop/mobile; автоматизировать в пределах существующей инфраструктуры, ручные проверки указать в отчёте.
- Выполнить `go test ./...`, race-тесты затронутых пакетов, `go vet ./...`, `go build ./cmd/hub`, `npm run build` в `web/` и `git diff --check`.
