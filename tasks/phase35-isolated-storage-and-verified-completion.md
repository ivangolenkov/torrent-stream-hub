## Цель И Границы

Разные infohash не должны писать в одни физические файлы. Наличие final-файла правильного размера не является доказательством hash-verification и не должно разрешать direct read, download или seeding непроверенных данных.

Входит: versioned storage layout, безопасная миграция старых загрузок, проверка completion и интеграция со всеми потребителями путей. Не входят: дедупликация payload, произвольный импорт файлов, полный upstream-аудит, прочие находки аудита. SQLite остаётся основной БД; формат существующего completion backend меняется только в необходимом объёме.

## Контракт Изоляции — F05

- Новый layout: `<DownloadDir>/payload/<canonical-infohash>/<relative-metainfo-path>`. Версию layout и относительный storage root сохранять явно; не определять их угадыванием существующих каталогов.
- Идентификатор — каноническая идентичность торрента из engine, не отображаемое имя и не произвольный ввод клиента. Проверить v1/v2/hybrid и aliases: повторное добавление одной раздачи не создаёт два владельца/корня.
- Использовать один layout provider для storage writer, direct stream, download/ZIP, manifest удаления и `.part`; HTTP/API продолжают показывать прежние логические имена и индексы.
- Служебные данные не размещать в адресуемой metadata области. Проверять reserved namespace: существующий legacy-торрент может уже владеть путём `payload/...`.
- Не использовать существующий занятый target, symlink или hardlink как изолированное хранилище без проверки. Чужие данные не перезаписывать и не удалять.
- Writer должен иметь containment-гарантии, а не только reader/delete. Проверить открытие, mkdir, rename final/part и повторное открытие через symlink; при необходимости расширить локальный storage backend.

## Совместимость И Миграция Старых Данных

1. До разрешения payload-записи инвентаризировать зарегистрированные legacy-пути и завершить/отложить pending deletion из фазы 34. Metadata-pending/неоднозначные записи не трактовать как свободные пути.
2. Сохранить versioned mapping и durable migration intent с исходным/целевым manifest и стадией. Во время миграции запретить передачу, запись и удаление мигрируемого экземпляра; не держать глобальный lock на весь перенос.
3. Автоматически переносить только доказуемо принадлежащие одному торренту regular files, включая `.part`. Не переносить весь каталог по имени и не перезаписывать существующий target.
4. Общие пути разных хешей, неизвестное владение, alias или конфликт namespace блокируют соответствующие записи с понятной диагностикой. Не выбирать владельца случайно и не запускать их запись в старый общий путь.
5. Использовать rename, когда это безопасно; если нужен copy fallback — только с контролем свободного места, временным target и проверкой результата. При недостатке места сохранять источник и откладывать миграцию.
6. После переноса выполнить проверку содержимого; только затем переключить активный mapping. Старые completion marks не являются доказательством корректности нового storage.
7. После прерывания между файловой операцией и commit распознавать источник/target по journal и безопасно продолжать. Два экземпляра payload не должны становиться одновременно активными; удаление источника допустимо только после подтверждённого commit и владения.
8. Сохранить политику temporary/permanent, FIFO, metadata и пользовательские file priorities. Обновлять deletion manifests согласованно с mapping.

В README описать резервное копирование, объём дополнительного места для copy, действия при конфликте и процедуру восстановления. Downgrade на бинарник со старым layout после миграции не поддерживать молча: явно предупредить и определить способ возврата из backup.

## Контракт Проверенности — F06

- Разделить presence/size, persistent completion hint и verified completion текущего поколения storage.
- Убрать присвоение verified complete только из final-имени и размера. Проверить `setCompletionFromPartFiles()`, initial checks и `ReadyForDirectRead()` в локальном форке.
- Консервативная политика этой фазы: после старта/повторного открытия и миграции существующие данные проверяются hash-алгоритмами metadata перед признанием готовыми. Старые Bolt completion records могут служить подсказкой, но не обходят проверку.
- Выполнять verification асинхронно, с ограниченной параллельностью и отменой при Delete/Close; не читать весь payload в RAM и не вводить mmap payload. Не блокировать глобальный lifecycle lock на hash-проход.
- Во время проверки допустима выдача уже проверенных pieces через torrent reader, но не непроверенных. Проверить responsive reader: он не должен обходить новую гарантию. Seeding также не должен рекламировать/выдавать непроверенные pieces.
- Direct stream и готовый HTTP-download/ZIP разрешены только при verified completion всех затронутых pieces, безопасном открытии и совпадении файловой идентичности/размера. HEAD сам по себе не запускает загрузку и не создаёт stream session.
- Для multi-file учитывать граничные pieces, v2 alignment и нулевые файлы. Повреждение отзывает готовность, а не маскируется историческим `downloaded=MAX(...)`.
- При обнаружении изменения файла/поколения storage отзывать trust и повторять проверку. Документировать предел: неизменность содержимого во время передачи предполагает отсутствие внешнего writer; подмену с сохранением всех атрибутов нельзя обнаружить одним stat.
- Download-readiness должен опираться на verified status, не на сохранённый процент. Полный редизайн статистики F20/F21 вне фазы; старые значения не могут обходить новую проверку.

## Тестирование

- Два разных infohash с одинаковыми именами/путями и разными bytes: независимые download, verification, stream, удаление одного не затрагивает другой. Повтор одного хеша идемпотентен.
- Legacy single/multi-file, partial/final, paused и metadata-pending; сохранение FIFO/политики/приоритетов, занятый target и legacy namespace `payload`.
- Shared legacy paths: отсутствие автоматического выбора владельца, записи и потери данных; диагностируемая блокировка только затронутых записей.
- Прерывания до/после rename/copy/DB commit, ENOSPC, ошибки БД, readonly, restart/retry и cancellation; источник не теряется.
- Symlink/alias для source/target и компонентов пути, malicious metadata, конкуренция с cleanup/передачей; writer не выходит за разрешённый root.
- Final-файл корректного размера с неверным содержимым, устаревшие persistent completion records, замена после проверки: нет преждевременного direct read/download/seeding.
- Правильный файл после verification, shared boundary piece, v2/hybrid, нулевые файлы; ограниченная память и корректный shutdown во время проверки.
- Корневые проверки: `go test ./...`, race для `internal/...` и `cmd/...`, `go vet ./...`, `go build ./cmd/hub`, `npm run build` в `web/`, `git diff --check`.
- Отдельно во вложенном `pkg/anacrolix-torrent`: тесты корневого пакета и `./storage`, включая новые regression-тесты, race для изменённых пакетов. Корневой `go test ./...` их не запускает. Полный набор форка запускать при доступности внешних зависимостей; ограничение `libpossum` не скрывать и не подменять им запуск затронутых пакетов.
