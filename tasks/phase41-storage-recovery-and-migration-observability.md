# Фаза 41: Восстановление хранения и наблюдаемая миграция

## Статус и зависимости

Финальный macOS `make check` и полные native Linux root/fork race suites с vet прошли; Windows suites cross-compiled, но нативно не исполнены. Результаты и оставшийся внешний gate: [отчёт](implementation/phase41-report.md), [wire-контракт](phase41-recovery-contract.md).

- Основание: анализ логов последнего рестарта пользовательского Docker-инстанса с downloads на HDD и сопоставление с текущим кодом. Наблюдения и ограничения доказательств приведены ниже; реализация не должна зависеть от истории чата или файлов в `/tmp`.
- Начинать реализацию после отдельной команды пользователя. Блоки выполнять последовательно, проверяя затронутые гарантии перед следующим блоком.
- Отчёт после реализации или значимого блока: `tasks/implementation/phase41-report.md`. Фазу 42 автоматически не начинать.

## Цель и границы

Дать пользователю безопасный путь восстановления после конфликтов старых файлов и прерванных удалений; устранить гонку проверки владения с изменением каталога; показывать реальную причину недоступности торрента и ход долгой миграции на HDD.

В scope входят Go, SQLite, локальный форк `anacrolix/torrent`, REST API, Vue, совместимость сохранённых данных, документация и регрессионные тесты. Новые recovery-команды должны работать через те же coordinator, ownership и verification gates, что и обычные команды.

Не входят возврат режима `.part`, автоматическое удаление конфликтующих копий, произвольное объединение повреждённых файлов, параллельная миграция всех торрентов, переписывание torrent engine, новая БД и обновление зависимостей без связи с находками. Ускорение диска не обещается: сначала измеряется стоимость этапов и устраняется отсутствие наблюдаемого прогресса.

## Сохраняемые гарантии

1. Runtime пишет в имена из metainfo без добавления `.part`. Настоящие metadata-файлы и каталоги с таким расширением остаются обычным payload.
2. Только проверка фрагментов текущего открытия разрешает чтение, upload и completed-file fast path. Имя, размер, hash отдельного файла, старый completion или успешное копирование сами по себе не дают torrent readiness.
3. Rooted операции, isolated roots/aliases, no-replace publication и защита чужих/служебных файлов сохраняются. Конфликт не разрешается перезаписью или удалением неизвестной копии.
4. SQLite остаётся единственной БД: WAL, настроенный пул и короткие транзакции. Дисковый I/O и hash-проходы не выполняются внутри длительной SQL-транзакции или под общим engine/coordinator lock.
5. Каждая recovery-операция связана с record identity и собственной версией операции. Старый callback, retry или запрос не влияет на повторно добавленный тот же infohash.
6. HTTP и диагностика доступны во время migration/recovery. Сохраняются CORS `*`, TorrServer-совместимость, stream reference counting/debounce, admission limits и sticky DiskFull.
7. Отмена ожидания не считается мгновенным завершением зависшего OS syscall. Ресурс нельзя закрывать или передавать новой операции до завершения владеющей им задачи.

- Добавить малые fixtures: final + sidecar с одинаковыми и различными данными; pending deletion до и после удаления части файлов; migration A с одновременным Delete/re-add B; большой логический файл с управляемым медленным reader/writer.
- Воспроизвести F41-03 с барьерами между чтением списка торрентов и чтением storage metadata другой записи. Если механизм отличается от гипотезы, зафиксировать найденную причину и скорректировать конкретное исправление без расширения scope.
- Закрепить контракт причин и действий: конфликт legacy-файлов, pending deletion, смена каталога с повтором, ожидание миграции, активная миграция, ошибка attachment и нехватка места. Разделить состояние layout, доступность runtime и готовность проверенных данных.
- Предусмотреть additive API-поля для причины, версии операции, разрешённых действий и прогресса. Сохранить существующее поле `error`; клиент не должен разбирать текст Go-ошибки. Точные JSON-имена закрепить в Go/TS contract tests и документации до подключения GUI.

## Блок 2 — F41-03: Проверка владения при изменении каталога

Точки входа: `internal/usecase/temporary_files.go`, `storage_migration.go`, `internal/repository/storage.go` и существующий coordinator.

- Получать согласованный набор identity/mapping/ownership данных; чтение metainfo и filesystem выполнять вне SQL-транзакции. Перед публикацией результата перепроверять использованные версии и закреплять необходимые ownership reservations.
- Различать исчезновение прежней записи, новую запись с тем же hash и реальный конфликт путей. `sql.ErrNoRows` нельзя безусловно игнорировать: повторно добавленный торрент или новый alias может владеть тем же payload.
- При изменении каталога заново строить проверку с ограниченным числом попыток и отменяемым ожиданием. Исчерпание попыток даёт диагностируемое временное состояние, а не постоянную ошибку «restore metainfo» и не бесконечный busy loop.
- Сохранять защиту на границе между проверкой и изменением файлов: параллельный Add/migration не должен получить пересекающийся root после успешного preflight.
- Для старых `blocked` с общей ошибкой разрешить повторную проверку по актуальному каталогу. Не очищать ошибку и не подключать runtime до успеха; pending deletion имеет приоритет и не снимается этим retry.

## Блок 3 — F41-02: Завершение и отмена pending deletion

Точки входа: `internal/usecase/torrent_uc.go`, `temporary_files.go`, `internal/repository/cleanup.go`, deletion lifecycle tests.

- Описать переходы удаления: intent сохранён → runtime остановлен → manifest готов → удаление файлов → удаление записи; отдельно retry, cancel requested и cancellation completed. Сохранять достаточные данные для восстановления после любой границы.
- Retry продолжает исходный сохранённый режим и manifest, повторно проверяя ownership. Несовпадающий `delete_files` возвращает 409 с отдельным кодом, текущим режимом и доступными действиями; не превращать его в неявную смену операции.
- Добавить явную отмену дальнейшего удаления. Сначала durable cancellation и прекращение admission старой задачи, затем остановка/ожидание текущего worker. После подтверждения отмены не допускаются следующие unlink и удаление записи старым worker.
- Отмена сохраняет оставшиеся данные, но не восстанавливает уже удалённые. Запись остаётся остановленной; состояние сообщает о частичном либо неизвестном объёме удаления. Перед возобновлением обязательна проверка оставшегося payload; автоматическая загрузка не начинается.
- Старые cleanup manifests без сведений об уже выполненных unlink считать неопределёнными, а не доказательством сохранности. После отмены можно отдельно удалить только запись, сохранив оставшиеся файлы, либо явно возобновить торрент с проверкой данных.
- Разделить отмену HTTP-запроса, shutdown и явную отмену операции. Первые два события не стирают durable intent. Повтор команды и рестарт не должны ни возрождать отменённую задачу, ни терять незавершённую.
- Согласовать manual delete и temporary cleanup: единый lifecycle, защита активных transfers и новых поколений записи. Не вводить отдельный обход safety gates для recovery API.

## Блок 4 — F41-01: Разрешение конфликтов обычного имени и `.part`

Точки входа: `pkg/anacrolix-torrent/storage/file-import-part.go`, storage adapter, usecase recovery и repository journal.

- Оставить открытие конфликтующего storage неразрушающим; вернуть типизированную причину и относительный metadata path. Обычный startup/Resume не запускает скрытое объединение или многократный полный анализ кандидатов.
- Добавить отдельную ограниченную по ресурсам операцию анализа. Сравнивать содержимое потоково; для проверки пригодности использовать metainfo и существующий verifier, учитывая v1 pieces на границах файлов, v2/hybrid и неполные данные. Размер и timestamp не определяют лучший кандидат.
- Результат различает одинаковые копии, подтверждённый пригодный кандидат и неоднозначность. Показывать доступные сведения и ограничения проверки; при неоднозначности требовать явный выбор, сохраняя альтернативу. Автоматическое объединение разных наборов валидных pieces не входит в фазу.
- Реализовать явное применение выбранного варианта через durable journal: зарезервировать операцию, закрыть доступ runtime, сохранить альтернативный файл в защищённом каталоге восстановления на том же filesystem, опубликовать выбранное содержимое под metadata-именем без перезаписи и выполнить verification.
- Каталог восстановления принадлежит приложению, не пересекается с torrent metadata и не очищается обычными torrent/temporary cleanup. Отображать наличие сохранённой копии и занимаемое место; её удаление не является побочным эффектом успешного Resume.
- До каждого изменения повторно проверять identity/version, ownership и идентичность проанализированных файлов. Изменившийся кандидат, symlink/hardlink, неподдерживаемая операция, DiskFull или отказ flush оставляет данные доступными для повторного восстановления и выдаёт конкретную ошибку.
- Проверить прерывание между сохранением journal, перемещением альтернативы, публикацией и verification. Повтор операции не создаёт бесконечные резервные копии; журнал никогда не разрешает уничтожить единственный экземпляр данных.
- Сохранить совместимость с существующими migration journals: recovery не перемещает пути, которыми ещё владеет незавершённая миграция.

## Блок 5 — F41-04/F41-05: Диагностика, прогресс и GUI

- Ошибка final + sidecar возвращает 409 с конкретным кодом, а не общий 500. Неожиданные I/O/DB errors не маскируются под конфликт. Одинаковые причины доступны через action response, список/детали торрента и SSE; внутренние абсолютные пути не нужны для выбора действия.
- `storage_state=ready` описывает layout, но не означает успешный runtime attachment. При отказе показывать отдельную причину и действие восстановления. Известные сохранённые metainfo не отображать как ожидаемые только из-за отсутствия runtime.
- Для pending deletion показывать исходный режим, этап, последнюю ошибку и retry/cancel. Не предлагать обычный Resume или противоположный delete как исправление; пояснять последствия отмены при уже удалённых файлах.
- Для миграции показывать очередь и этапы `preflight`, чтение исходников для checksum, `copy`, `verification`, `cleanup`; для восстановления файлов — соответствующий этап операции. Отличать этап завершения миграции от окончания runtime verification.
- Ввести измерение обработанных/ожидаемых байтов для текущего этапа и текущего файла, количество файлов, время начала этапа, время последнего изменения счётчиков и последнего heartbeat. Не суммировать повторные чтения в ложный общий процент; при неизвестном total показывать неопределённый прогресс.
- Обновлять счётчики внутри чтения/copy/verification, а не только после закрытия файла. Во время длительной операции публиковать heartbeat не реже одного раза в 5 секунд, даже если I/O ещё не вернул результат; heartbeat не должен сам выполнять filesystem I/O и не считается подтверждением продвижения байтов.
- Сохранить ограниченные очереди/latest-only публикацию. Не писать SQLite journal и не логировать каждый chunk: прогресс наблюдательный, durable checkpoint отвечает за crash recovery. Подавлять одинаковые ошибки, сохраняя первую причину и счётчик повторов.
- Зафиксировать последовательную миграцию как текущую политику HDD. После сбоя одного торрента остальные должны получать обработку; blocked retry не захватывает очередь бесконечно. Скорость/ETA не обещаются при недостаточных данных.
- Ввести тестовые счётчики I/O и journal writes: публикация прогресса не добавляет полные чтения данных и записи journal на каждый chunk. Для профиля «много мелких файлов + один крупный» записать длительность этапов и объём I/O в отчёт.

## Обязательные сценарии проверки

| Область | Сценарии и ожидаемые свойства |
| --- | --- |
| Конфликт файлов | Одинаковые копии; одна повреждённая; разные неполные; metadata name с `.part`; v1 граница двух файлов; v2/hybrid; zero-length. Альтернатива сохраняется, readiness зависит от verification. |
| Recovery crash | Сбой/рестарт после каждого шага journal и перемещения; отказ flush, target exists, изменение кандидата, DiskFull. Повтор не перезаписывает чужие данные и не теряет единственную копию. |
| Deletion lifecycle | До первого unlink, после нескольких unlink, старый manifest без progress, shutdown, повтор cancel/retry, HTTP disconnect. После завершённой отмены нет дальнейшего удаления; уже удалённое не объявляется восстановленным. |
| Конкурентность | Migration A + Delete B; Delete/re-add B с тем же hash; Add/alias между preflight и publication; cancel + retry + re-add. Нет ложного permanent blocked, stale effects и обхода ownership. |
| Представление | Ready layout + failed attachment; metadata known + runtime absent; deletion pending; legacy queued; moving. REST, SSE и GUI согласованы; late snapshot не возвращает старую причину или прогресс новой записи. |
| Долгое I/O | Один файл больше всего малого fixture, управляемая задержка hash/copy/verify и блокированный syscall. Байты меняются внутри этапа; при блокировке остаётся heartbeat с неизменным last-progress. |
| Ресурсы | Нет чтения полного файла в RAM, journal write на каждый chunk, дополнительного hash-прохода для GUI или worker на каждое обновление. HTTP/SSE доступны при занятом storage worker. |
| Upgrade | Существующие ready/legacy/blocked/moving и pending deletion после SQLite upgrade/restart. Нет сброса intent, completion считается подсказкой, sticky DiskFull сохраняется. |

Детерминированные тесты используют barriers/fake clock/injected I/O; ожидание реальных многогигабайтных файлов и публичного swarm не требуется. Для repository нужны настоящие временные SQLite базы. Интеграционные проверки включают настоящий файл, root adapter и restart/reopen, а не только моки.

Итоговая локальная приёмка: `make check` (frontend tests/build, root tests/race/vet/build, отдельные fork `.`/`./storage` tests/race/vet). При изменении других пакетов форка расширить набор. Для новых filesystem/recovery сценариев обязательны native Linux, macOS и Windows storage checks; cross-compile не заменяет исполнение. Измерение HDD отдельно описывает окружение и не становится нестабильным CI-порогом по скорости диска.
